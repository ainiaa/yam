# System entry

Author: Jeff.Liu.

The exclusive ready background owner installs the native tray and the official Rust global-shortcut plugin. GUI, CLI and helper processes do not install a second tray or shortcut. The tray shows bounded running/unread counts (or unavailable), Open YAM, Pause notifications, and the explicit **Stop all tasks and quit** action. Tray status refresh uses in-process state and does not keep an otherwise idle owner alive. Ordinary window close/quit retains background task ownership.

Open sends a bounded desktop event when the GUI heartbeat is fresh and always launches the current executable once with zero arguments through the normal single-instance route. A recent heartbeat is not proof that a GUI is still alive. The existing window route shows/focuses the window and preserves pending real notification selection. This action does not create tasks, claim terminal input or execute command text. Stop all calls the existing owner cleanup directly; failed cleanup restores admission and does not exit.

The fixed global shortcut is **CommandOrControl+Shift+Y**. It starts disabled and is enabled only by an explicit checkbox in the normal window's **System entry** settings. The private version-1 preference stores only `global_shortcut_enabled`; it is bounded to 4 KiB. Missing, malformed or nonprivate/nonregular input falls back to off with a visible warning. Requested and registered state are distinct, so registration conflicts, unregister failures and save failures remain visible. The normal window remains the fallback. No JavaScript shortcut SDK or arbitrary shortcut-command configuration is provided.

Notification pause is owner-authoritative. Its snapshot contains only paused, revision, owner_instance and established. The first GUI migration seeds the legacy `yam.notificationsPaused` value once, fenced by the current authenticated owner. An explicit tray choice wins that migration. After establishment, focus messages carry selection only; legacy pause fields cannot overwrite the current choice. Explicit changes use owner-instance and revision compare-and-set. The frontend mirrors only accepted snapshots, refreshes after an owner/gap/conflict, rejects stale replies, and retains a newer same-owner event arriving during either an initial snapshot read or a later refresh. Before the first GUI seed, a selection request fences lifecycle delivery even before the first poll heartbeat. With no GUI/selection request, the owner default stays unpaused. Bridge and direct lifecycle notification paths share this state; reading/toggling it does not initialize history or an Agent Bridge.

The locked dependencies are Tauri's `tray-icon` feature and `tauri-plugin-global-shortcut` 2.4.0, installed only for the desktop target. Plugin setup runs on the native main thread after exclusive owner readiness. Register/unregister and tray operations release business/settings locks before waiting on main-thread dispatch. No dependency resolution is repeated during locked verification.

The automated evidence exercises shared owner operation bodies, authenticated localhost fixture transport, actual extracted App callbacks/effects and rendered settings with mock IPC/OS operations. It does **not** establish native tray menus, shortcut conflict behavior, window reopening, permissions or Windows/Linux operation. Those native checks and the formal provider coverage gate remain pending/uncovered. No real owner, GUI, Agent or user namespace was launched. See [T11 evidence](evidence/yam-system-entry-t11/README.md).

Primary references: [Tauri system tray](https://v2.tauri.app/learn/system-tray/) and [official global shortcut plugin](https://v2.tauri.app/plugin/global-shortcut/). Linux tray behavior depends on the platform tray implementation.
