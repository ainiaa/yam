## Minimal design

Use one `scripts/third_party_notices.py` module/CLI for offline collection, manifest validation, deterministic byte rendering and bundled-report validation. Use Python 3.11+ `tomllib` for Cargo.lock; fail clearly when unavailable instead of adding a parser dependency. Store original bodies in one content-addressed directory and an explicit source manifest. Do not build a SPDX policy engine, license classifier, target-reachability engine, downloader, source crawler or generic audit framework.

The inventory is all 535 registry identities in the currently bound Cargo.lock plus the exact 12 npm production identities, including scheduler and the installed Tauri plugins. Node's official aggregate LICENSE remains an additional distribution component, not a thirteenth npm package. Treat 535/12 as this frozen input set, not perpetual magic counts or proof every Cargo package is linked. Match sets of full identities; do not accept count equality. Exclude only the explicitly named first-party workspace identity. Other git/path dependencies produce an explicit unsupported-source gap.

For Cargo, parse the actual lock and key records by name/version/source/checksum. For npm, the simplest dependency-free option is a checked-in, already reviewed 12-identity inventory bound to the exact pnpm-lock.yaml and package.json hashes, corroborated against the installed production tree using the existing `pnpm --dir apps/desktop list --prod --json --depth Infinity`. Deduplicate repeated peer references by actual name/version/source identity while retaining their source binding. Validate package.json identity at each resolved installed path, including scheduler reached below react-dom. Do not hand-roll a YAML parser or import an internal pnpm YAML module. The local pnpm 9.15.1 help supports list/prod/json/depth; it does not advertise a `list --lockfile-only` switch, so do not invent one. Installed-tree output alone is not proof of lock integrity: the frozen npm inventory must retain its existing lock/tarball-integrity/exact-source receipt chain. Any lock/package.json digest drift requires explicit inventory regeneration/review and fails release; a stale installed tree cannot silently redefine expected identities.

Offline collection inspects checksum-verified cached .crate archives and installed npm files, plus the exact-source original bodies and provenance receipts already collected in the prior two rounds. Do not rerun upstream discovery/download in this slice. Read archive members directly, never extract arbitrary members. Collect explicit license-file and actual LICENSE/LICENCE/COPYING/NOTICE/COPYRIGHT text candidates, including relevant nested/vendor notices; a source code filename merely containing copying is not a body. Preserve all selected original bytes, distinct NOTICEs and identity-to-body mappings even where body hashes are shared. Missing, declaration-only, unsupported-source and provenance-uncertain records remain gaps. Finding a root LICENSE does not by itself certify all embedded third-party notices. An exact manifest selects source-backed bodies; filename/SPDX matching cannot silently change a gap to complete.

The current 26 Cargo + 2 npm gaps remain visible and release-blocking. Reuse their existing evidence; do not replace them with canonical templates, infer copyright holders or select a legal policy. Full 535+12 collection may reveal additional gaps; the earlier bounded passes do not establish completeness of every other identity. A deterministic INCOMPLETE report is a valid useful collector result.

## Report and byte renderer

Use one exact versioned report shape: lock/input digests, collector/renderer schema and implementation digest, exact expected identities, per-identity body hashes and provenance/status, sorted gaps, rendered-notices hash and mode. Full original bodies live as bytes keyed by SHA256; report paths are constrained local relative paths. There is no network operation in collection/render/validation. Existing source receipts are inputs, not readiness booleans.

Only mechanical completeness with exact identity equality, verified body/source bindings and zero gaps may produce `license_ready: true` in release mode. This term means the mechanical notice gate passed, not license compatibility approval. Developer reports omit that field and use explicit `coverage_state: incomplete|complete` plus `release_eligible: false`. A supplied ready flag alone is never sufficient: validation recomputes hashes, set equality, statuses and deterministic rendered bytes. Preserve Node's aggregate and existing headless/serializer/five frontend license body bytes; retain their package headings/mappings. Preserve CRLF/Unicode/leading whitespace inside original bodies. Add renderer separators around bodies without rewriting them.

Freeze finite I/O limits rather than accepting arbitrary archives/JSON: suggested lock/report cap 16 MiB each, per original body 8 MiB, selected cumulative body bytes 128 MiB, per .crate compressed archive 256 MiB, per archive inspected headers 20,000, and inventory maximum 4,096 identities. Stream archive SHA256 and selected member reads, reject duplicate/escaping/absolute members and selected links/devices, invalid UTF-8 or whitespace-only text, and output budget overflow. Check exact package prefix and explicit license-file containment. A body exceeding the chosen budget is an explicit gap/rejection; never truncate it. These are engineering limits to freeze internally, not new user licensing decisions.

## Two modes and the exact gates

1. Ordinary developer/native builds pass explicit `--notice-mode developer`. They may build with recorded coverage gaps, but emit only `DEVELOPER-THIRD-PARTY-NOTICES.txt` and a developer report with a prominent `INCOMPLETE — DEVELOPER VALIDATION ONLY` header when gaps exist. Even a complete developer collection says developer-only and cannot be presented as release-ready. Never replace the formal notices or formal readiness report in developer mode.
2. Add one `apps/desktop/src-tauri/tauri.release.conf.json` overlay. Its before-build hook passes explicit `--notice-mode release`, and its resource array selects the runtime plus `THIRD-PARTY-NOTICES.txt` and the formal report. The default Tauri config selects the developer-named resources/hook. Add one documented package command for `tauri build --config src-tauri/tauri.release.conf.json`. Confirm effective merged configuration in tests; resource arrays must replace the default developer list rather than accidentally bundle both. Do not add a build mode to macos-release.py: it is currently a post-build checker, and retaining that responsibility is simpler.
3. In build-terminal-runtime.py release mode, validate all offline inputs and fully render notices in memory/private staging before any Node `--check`, `--build-sea`, temporary SEA creation, ad-hoc signing, or final binary/notices/report replacement. Known incomplete/stale/invalid reports must exit before those effects. Prefer running the Cargo/npm gate before runtime preparation; Node's aggregate must also come from its checksum-verified official distribution before the final gate succeeds. Missing required local notice sources fail formal mode rather than triggering source discovery. The collector stays offline; existing developer runtime acquisition is a separate existing behavior.
4. After a successful SEA build/probe, stage final notice/report bytes before promotion. Publish the release report last and bind it to the final runtime and notice hashes. Do not claim multiple os.replace calls are an atomic transaction. On a failed or interrupted promotion, a mismatched/missing report makes the resulting bundle ineligible; do not add a recovery journal merely to simulate multi-file atomicity. In particular, missing/stale/incomplete preflight must leave prior final binary/notices/report byte-for-byte untouched.
5. macos-release.py check/notarize/sign-notarize must validate the bundle's exact formal notices/report resource location, current expected input/manifest bindings, complete set and hashes before calling signature, security, codesign, ditto, notarytool or stapler. A developer artifact, missing report, false/absent readiness, incomplete body set, altered notices/runtime, stale lock/manifest or unknown schema fails closed. Keep its existing redacted error categories. Do not search arbitrary files for a ready string. This downstream check is defense in depth and does not pretend to retroactively guard an earlier raw Tauri build.

No skip/readiness environment variable can promote developer to release. The formal CLI/config has an explicit release argument that wins over inherited developer settings. Users can still build a private developer bundle, but it cannot pass the formal checker. This does not prevent someone from deliberately editing the scripts or bypassing the checker with external signing tools; that is outside the engineering gate claim.

Boundary:

- Exact identity-set mismatch despite equal count; duplicate identity; extra/missing identity; same name/different version/source/checksum; nonregistry dependency; both lock digest and package.json drift; stale installed npm tree, absent scheduler alias and changed package identity.
- Exactly-at-limit bodies/report and one byte over; malformed UTF-8, CRLF/Unicode preserved, empty/metadata-only/declaration-only body remains gap, archive duplicate/member traversal/link/device and declared oversize rejected without extraction.
- Body hash/provenance/report-schema/renderer digest mismatch; release cannot accept a manually toggled ready boolean; developer artifact is rejected even if it happens to contain every body.
- Inherited skip/developer/ready environment values cannot bypass explicit release mode. Effective release resources contain only formal notices/report, default resources only developer notices/report.
- The real full inventory operation reports all 535+12 identities with explicit known 26+2 gaps still present; this is an INCOMPLETE outcome, not a release PASS. Do not assert a smaller final gap count without new authoritative evidence.

Exception/ordering:

- Invoke actual release builder main with missing, stale, corrupt or incomplete inputs and pre-existing binary/notices/report sentinel bytes. Assert exact unchanged sentinels, zero Node check/build, zero temporary SEA, zero codesign, zero final replacement. Read/parse/permission/time-limit failures take the same rejection path.
- Inject render/write/SEA/probe failure: no ready report can describe an unverified new binary; private temporary files are cleaned without deleting another writer's files. Do not promise rollback of arbitrary already-promoted files after an I/O failure; validate the conservative report-last failure state.
- For each macos-release mode, supply missing/developer/stale/altered report and assert zero signing/notary/staple/archive subprocesses. Include a signed/notarized-looking fixture so signature metadata cannot bypass notices. CLI error output must not expose certificate/profile/exception argv.
- Any collection/network stub invoked unexpectedly fails the test; archive/cache/source bodies and earlier receipts remain byte-identical. No live network/native/signing in this matrix.

Run the targeted real Python tests first, then required existing Python release/runtime tests and project baseline checks after source freeze. A final offline collection report is independently reviewed as data. Native bundle resource inspection remains a separate later acceptance; no real signing, notarization or publication is authorized by this proposed source task.

## Review of Root's concrete draft and npm choice

Reviewed `/tmp/yam-t18-root-execution-contract.md` and Root's subsequent explicit npm collection choice. The smaller Root owned-path list and its `scripts/third-party-notices/` manifest/body directory supersede the example directory names above. No additional module, standalone YAML exporter, new release-build mode or new dependency is necessary. The contract can be frozen after these precise wording fixes; none requires a new user licensing choice.

1. **Npm integrity cannot be inferred from list JSON.** The observed pnpm list command is suitable for installed production closure, package identity, resolved URL and realpath. Do not append unsupported `--offline` or `--lockfile-only`. Its graph/URL output does not independently prove the archive SRI or parse the raw pnpm lock mapping. Keep the reviewed exact 12-entry npm identity/source/integrity mapping as a section of the same frozen manifest, bound to the whole raw lock SHA256 and production-declaration fingerprint; do not add a second seed file. Collection compares the bounded actual graph against that section, validates installed package identities and imports the source/tarball-integrity evidence already available. A complete entry needs a real existing source binding: an independently verified original archive/SRI, or the already verified immutable source-identity/body receipt chain with its limitations retained. If the lock-to-source mapping or body provenance for an entry has never been verified, record `provenance_unverified` rather than manufacturing verification from the graph URL. Such additional gaps are acceptable in developer mode and block release. Updating the lock invalidates the reviewed mapping until an explicit new collection/review; the code need not automatically understand arbitrary future YAML. This is the smallest honest parser-free binding for this frozen source slice.

2. **Avoid self-invalidating package.json hashes.** Replace the draft's unqualified `packageJSON digest` requirement with a canonical hash of production dependency declarations (`dependencies`, `optionalDependencies`, and any other root declaration category actually used by the chosen production graph). Explicitly sort keys and preserve declared values; reject unexpected structural forms. Include the root package identity if useful. Script-only additions to wire the formal build must not invalidate their own manifest. The raw pnpm-lock SHA256 remains mandatory and exact. This adopts Root's latest choice and supersedes my earlier whole-package.json suggestion.

3. **Separate collection from rendering.** Only explicit offline collection invokes bounded local pnpm list and reads local Cargo/npm caches. Renderer and macOS post-build checker use the checked-in bound manifest, original body bytes, current lock/declaration digests and deterministic hashes; they require no installed pnpm or Cargo cache. They must not invoke pnpm merely to validate a packaged report. Freeze local graph limits, e.g. 10-second process deadline and 2 MiB captured JSON, with no shell, install, lifecycle or network fallback. Release-builder tests asserting zero subprocess calls refer to runtime Node/SEA/native build effects after pure preflight; package-manager collection is a separate preparatory invocation. Root's phrase `before any runtime Node subprocess` correctly preserves this distinction.

4. **Narrow the failed-release preservation promise.** Missing/stale/incomplete/invalid preflight and any failure before promotion preserve existing final binary/notices/report bytes exactly. Once multiple files are being promoted, arbitrary disk/rename failure cannot promise both all-old contents and no rollback. Stage every new output first; include final runtime SHA256, notices SHA256 and current manifest/input bindings in the release report, then atomically replace each file with the report last. Checker validates all of those bindings, never the complete flag alone. A partial promotion therefore fails closed without deleting an old report, force-deleting another writer's file, or adding a transaction/recovery framework. Use a test that fails each individual promotion step and proves no falsely valid bundle, while only pre-promotion tests promise all-old bytes. Binary-last is also possible if report binds the expected new binary hash, but report-last is the smaller explicit completion marker. Do not leave `publish before binary or equivalent` as an ambiguous unstated order.

The draft's separate developer notices/report and formal Tauri overlay are a justified minimal integration because the current macOS script is post-build. Preserve unchanged product/CSP/permissions and test the actual merged resource list. Source cache/body provenance resides in the manifest, which makes later CI render deterministic without collecting sources again. Do not silently count the Node aggregate as npm closure: bind it additionally to the pinned runtime distribution/version/checksum (and selected target where relevant), retaining its full upstream bytes.

Root's `complete=true` mechanical report spelling is sufficient; a second `license_ready` flag is unnecessary. Developer mode must always be ineligible for the formal checker, even if its source coverage eventually reaches complete; its mode and distinct artifact name enforce that. The current DEVELOPER-INCOMPLETE wording is accurate for the known gaps. If coverage later becomes complete without a release build, retain DEVELOPER VALIDATION ONLY and avoid falsely describing the source set as incomplete; this is a label condition, not another build mode.

With these corrections, the proposed source slice is finite and technically ready: implement the offline evidence-backed collector, preserve the current gaps, support explicitly incomplete developer builds, and refuse formal builds/delivery until complete exact provenance and bytes exist. It is not a proposal to resolve missing authoritative license texts, approve policy or certify all 535 packages from a previous sample.
