# T13 safe cleanup: native isolation probes (Git 2.54.0)

Scope: owned `tempfile` repositories and linked worktrees only. No project business source, user repository, or user/common Git config was edited. No force, recursive deletion, prune, or hand-written Git worktree registry operation was used. Git version was `git version 2.54.0`.

## Findings

1. **Shadow `$GIT_DIR` + real `$GIT_COMMON_DIR` + real object store/index:** Git did preserve the real worktree registry: on a clean unfiltered fixture, ordinary removal exited 0 and `git worktree list` dropped the target. It also read real common config: in the filter fixture, ordinary removal ran the sentinel clean filter three times and refused because the test filter made the unchanged checkout look dirty. The candidate shadow config did not override common config. Copying the target's real index into the shadow was necessary; an empty shadow index made Git conservatively call the target modified/untracked and refuse. Matrix and raw stdout/stderr are in `/tmp/yam-t13-cleanup-isolation-probes-raw.json`.

2. **`GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_GLOBAL=/dev/null` (and key-specific runtime config):** normal target remove succeeded; tracked dirty and ordinary untracked targets were refused; ignored-only files were deleted along with the worktree. With a configured local clean filter, it ran three times during removal and the operation refused. Global/system isolation therefore does not neutralize local/common configuration. Per-key `GIT_CONFIG_COUNT` overrides can suppress a known driver only when all relevant keys including `.required` are overridden; this is not a blanket filter-off mechanism and changes status semantics. The prior one-driver experiment is in `/tmp/yam-t13-cleanup-filter-override.txt`.

3. **`GIT_ATTR_SOURCE=<safe tree>`:** normal remove succeeded; tracked dirty and ordinary untracked targets were refused; ignored-only files were deleted. For a linked target whose committed `.gitattributes` enabled a sentinel clean filter, the safe source tree disabled it and removal succeeded with no sentinel call. That changes Git's cleanliness result: the same target under its actual attributes invoked the filter and was reported unclean (candidate 2 exit 128), while the source override skipped the filter and removed it (exit 0). Adding an active filter rule in the real `$GIT_DIR/info/attributes` still ran the sentinel three times and blocked removal; the info file has higher precedence than tree attributes. This is not safe as a general mask. All cases are in the matrix JSON.

4. **Atomic same-parent rename to YAM-owned quarantine, then ordinary `git worktree remove <old-path>`:** this succeeded for the actual registration-removal operation. The old registered path was absent, Git exited 0, the sentinel was not called, and `git worktree list --porcelain` no longer listed the linked worktree. Raw output is `/tmp/yam-t13-cleanup-quarantine-probe.json`; replay script is `/tmp/yam_t13_quarantine_probe.py`. This avoids a status/filter invocation for the absent registered path, but does not avoid loading the original local config. In an owned follow-up fixture, a malformed line appended to `.git/config` made this ordinary remove exit 128 with `bad config line 13`; the linked admin directory still existed. Restoring the config and retrying removed the registry successfully. Raw output is `/tmp/yam-t13-cleanup-quarantine-config-read.json`. This is only registry removal: the full worktree data remains in quarantine.

## Quarantine consequences and limits

The quarantine trick suppresses filter execution by ensuring no target files remain at the path Git checks; it is not a configuration sandbox. Git still parses local/common configuration needed to identify the repository. After Git removed the registration, the quarantine directory remained with its `.git` file still pointing at the now-deleted `.git/worktrees/linked` administrative directory. `git -C <quarantine> status` failed with `fatal: not a git repository: (null)`. `git worktree repair <quarantine>` failed with `unable to locate repository; .git file does not reference a repository`; the raw result is `/tmp/yam-t13-cleanup-quarantine-recovery.json`. Thus post-removal rollback is not a simple rename: the Git link target has already been deleted. Before the Git command succeeds, renaming quarantine back to the original path can restore the original linked-worktree layout if that path is still free. After it succeeds, no supported automatic recovery was demonstrated; preserve quarantine bytes and present explicit manual recovery rather than deleting them or claiming cleanup finished.

A safe implementation would need an owner-manifest transition that records a unique quarantine path and target inode before rename, verifies the exact directory identity immediately before and after same-parent atomic rename, and reopens deterministically after crashes. On restart: if the original path is still registered and quarantine exists, the operation must choose a verified rollback or retry; if the registry entry is gone but quarantine exists, retain the bytes as an orphaned-data state; if another object occupies the original path, do not touch it. There is an external race between preflight and rename (processes not coordinated by the app can still write through open handles), and another process could recreate the old path before Git's removal. The final Git command avoids content/status at the absent registered path, but the preflight still must accurately reject tracked modifications, untracked files, and ignored files without running filters. Git's own remove protects tracked changes and untracked files; our matrix confirms it removes ignored-only data, so the application needs its own ignored-file refusal before rename. The post-removal quarantine is not a Git worktree and is not yet safely disposed of. Permanent physical cleanup needs a separately designed, recoverable owned-directory deletion/trash strategy; rename alone is not acceptance.

No repository source patch is proposed in this probe. This evidence narrows the root cause: Git can remove the real registration without loading target filters if the registered filesystem path is absent, but doing so severs the quarantine's `.git` link before any physical data cleanup.

## Primary documentation

- [`git worktree`](https://git-scm.com/docs/git-worktree): ordinary `remove` is for clean worktrees and rejects untracked/modified content; docs describe metadata in `$GIT_DIR/worktrees` and how linked `.git`/`gitdir` pointers link the directory and registry.
- [`git` environment variables](https://git-scm.com/docs/git/2.53.0): `GIT_COMMON_DIR` redirects non-worktree metadata there, while worktree-specific state stays in `GIT_DIR`; this explains why a shadow `GIT_DIR` combined with the real common dir still consumes the real common repository context.
- [`git-config`](https://git-scm.com/docs/git-config): `GIT_CONFIG_GLOBAL` / `GIT_CONFIG_NOSYSTEM` select or skip global/system sources. `GIT_CONFIG_COUNT` adds runtime key-value pairs that override file values, but only for keys explicitly supplied.
- [`gitattributes`](https://git-scm.com/docs/gitattributes): `$GIT_DIR/info/attributes` has highest precedence, ahead of worktree `.gitattributes`; filter drivers require corresponding config and can run on check-in/status comparisons.
- [`git check-attr --source`](https://git-scm.com/docs/git-check-attr): source-tree attribute lookup is a tree-ish selection, not a mechanism for masking repository `info/attributes` or preserving the target's ordinary worktree-attribute semantics.
