# YAM AI Agent 工作台：核心体验收敛方案

作者：Jeff.Liu。原方案日期：2026-10-04；范围修订：2026-10-09。状态：按用户最新确认，以“舒适、易用地使用 AI Agent”为本轮唯一产品目标。原方案的 cmux 功能目录仅作背景参考，不再作为实现承诺或完成门槛。自动更新继续暂停。

执行记录见 [2026-10-08 进度与基线](2026-10-08-yam-cmux-terminal-parity-progress.md)。原审批版本 SHA-256：`e0aec654f995df880aabeb3a90b4b3658fd8f5c5b241c3cbdeeb79115bc3538f`。

## 1. 产品目标与范围决定

YAM 本轮要成为好用、可靠的本地 AI Agent 工作台。用户应能从项目快速启动 Agent、并行管理多个会话、看懂任务状态、切换和恢复工作，并可靠地输入、查看和复制终端内容。

核心要求：

1. **快速启动**：从选定项目和目录直接启动常用 Agent；已有 Profile/启动设置可复用，不强迫用户重复填写。
2. **并行管理**：多个 Agent 可用标签/面板区分；每个会话清楚显示其项目、目录和终端身份，切换不串会话、不丢当前查看位置。
3. **可信状态**：明确区分运行、等待用户、已结束、失败和未知；通知定位到正确会话。缺少可靠来源时显示未知，不推断 Agent 意图。
4. **可靠恢复**：隐藏、切换、关闭再打开界面不会意外丢失仍运行的任务；恢复界面不自动重启进程或重复命令。
5. **终端好用**：输入法、复制粘贴、搜索、滚动、快捷键、分屏和高输出下交互可用；查看旧输出时不被强制滚到底部。
6. **安全可控**：停止、重试或打开会话等操作针对明确目标；失败和不确定状态可理解、可恢复，不伪报成功。

本轮优先把已实现切片在真实桌面应用中验收并修复影响这些流程的问题。自动化测试通过不等于用户体验完成。没有证据证明当前 YAM 假死；压力测试用于发现用户可感知的问题，不预先定级为 P0，也不承诺绝对不假死。

## 2. 对标范围与基线

- 原始方案基线为 YAM `8fb2cb0`、cmux 稳定发布 `v0.64.25`。保留这些信息用于追溯历史差异。
- cmux 只作为具体交互的参考，不再以 cmux 的完整功能表衡量 YAM，也不要求把其产品线能力全部移植过来。
- 本轮目标用户是使用本地项目和 AI Agent 的开发者。需要本地/远程 SaaS 基础设施或独立客户端的方向不自动进入范围。
- 功能已具备源码和自动化测试、但尚未做真实桌面验收时，标记为“源码已交付、体验待验”，不得标为完整完成。
- 自动更新按已有决定暂停；Agent 原生协议不支持的能力不作为 YAM 缺陷。

公开 cmux 文档仅作对照参考，原链接留在此处供追溯；它们不是本轮需求清单。

## 3. 技术路线

继续采用当前 Tauri/Rust/xterm 技术路线。只有当真实 Agent 工作流遇到可复现、且无法用小改动修复的输入或渲染阻塞时，才评估终端引擎原型；不为追求 cmux 全功能或未经证实的性能优势启动迁移。不复制 cmux 实现代码。

## 4. 本轮范围与优先级

### P0：AI Agent 日常工作流必须可靠

| 能力 | 用户结果 | 完成边界 |
|---|---|---|
| 启动 Agent | 从项目/指定目录快速启动常用 Agent，复用已保存的安全配置 | 不建设通用插件或任意脚本执行框架 |
| 并行会话 | 多个 Agent 以标签/面板组织，身份清楚、可快速切换 | 先保证现有布局/窗口操作稳定，不为追求任意 Surface 重做架构 |
| 状态与通知 | 用户能知道哪个会话需要关注，并一键跳到对应终端 | 状态必须注明来源；不可靠时显示未知，不模拟或伪造审批 |
| 生命周期与恢复 | 隐藏/恢复界面不误杀、重复启动或串任务；停止目标准确 | 只恢复真实仍存在的会话；关闭后重启任务必须显式确认 |
| 终端交互 | 输入法、粘贴、搜索、滚动、复制和快捷键可用；高输出不阻断其他会话 | 优先修复可复现的用户痛点，不设脱离用户场景的吞吐竞赛 |
| 故障说明 | 启动、通信、停止和恢复失败能被用户看懂并采取下一步操作 | 不把未知结果显示为成功；诊断有界且不泄露敏感内容 |

### P1：只有支撑 P0 工作流时才做

- 常用 Agent 启动配置/Profile，以及项目和会话身份展示。
- 基本项目排序、命名、置顶、布局保存等组织能力。
- 基本 SSH 启动入口，仅在目标用户确实需要连接远程 Agent 时保留；不扩展成远程工作区平台。
- 基本文件路径、链接、结果查看和命令查找能力。

P1 已有源码功能不因范围收敛而删除；本轮不继续扩展其能力，除非真实验收发现它阻塞 P0 场景。

### 本轮明确排除

以下项目不属于本轮完成条件：完整 tmux/Zellij 互操作、Mosh/SSH 持续会话与远程转发、远程浏览器/文件传输、可配置 Dock、浏览器自动化、移动端、Cloud/团队/计费、企业 MDM、通用插件/动态 Surface、通用事件自动化。后续若有明确用户需求，再单独做产品和资源评估。

不要求“与 cmux 全功能对等”，也不以完成原有 A–F 清单作为发布门槛。

## 5. 有限的收口顺序

| 顺序 | 范围 | 用户可见结果 | 结束条件 |
|---|---|---|---|
| 1. 冻结核心流程 | 启动、并行管理、状态/通知、恢复、终端交互、停止 | 一组真实桌面验收用例与当前代码缺口清单 | 每条用例有明确通过/失败/不支持状态 |
| 2. 当前应用验收 | 使用包含当前源码的桌面构建验证 P0 流程 | 真实窗口、终端和 Agent 运行行为有记录 | 不用静态检查、模拟回调或旧构建代替当前应用验收 |
| 3. 修复阻塞项 | 仅修复验收中影响 P0 的可复现问题 | 核心流程按预期工作，缺陷有回归覆盖 | 修复后重跑受影响流程及回归 |
| 4. 收口交付 | 更新用户操作说明、已知限制和本轮结果 | 用户知道如何启动、切换、恢复和处理失败 | P0 通过；未验证项与明确排除项如实列出 |

不再创建新的 cmux 功能切片来填充完整性清单。若核心流程验收暴露新问题，按一个用户结果一个有限修复处理。

## 6. 核心体验验收标准

以下真实流程作为完成门槛，不要求与 cmux 做全功能或性能排名：

1. 从项目打开两个以上 Agent 会话，目录和会话身份正确，用户能快速切换。
2. 一个 Agent 需要用户处理时，状态和通知指向正确会话；无法确认时不显示伪状态。
3. 用户回看旧输出时继续产生新输出，画面不强制跳到底部；输入、复制和粘贴不丢失、不重复、不发往别的会话。
4. 关闭并重新打开窗口/应用后，恢复仍存在的会话与可恢复画面，不自动重跑已退出任务。
5. 停止一个 Agent 不影响相邻会话；失败时说明真实结果，不把未知结果当成功。
6. 高输出期间仍能操作其他会话；测得的延迟用于定位实际用户阻塞，不以单一吞吐数字代表体验，也不宣称未做的 cmux 对比。

每条流程在目标平台当前桌面构建上通过，且对应的自动化回归通过，才标记为完成。源码测试、打包成功和独立审查分别记录，不能替代原生验收。暂不覆盖的平台或协议差异明确标出。

## 7. 设计约束与影响面

- Rust owner 继续作为本地进程权威；显示身份（项目/窗口/面板）与运行身份（Agent/Session/PTY）保持区分。
- 会话状态和通知只使用可验证来源；Shell 文本或缺失事件不作为 Agent 已完成、已审批或可信 cwd 的证明。
- 界面重排、恢复和外观变化不得意外发送输入、接管会话或结束进程。
- 停止/重试按精确会话身份操作；不因 UI 状态猜测进程名并杀进程，不自动重复执行 Agent 命令。
- 复用现有 Tauri/Rust/xterm 与窗口结构；不为排除项预建通用 Surface、插件、远程控制或云端架构。
- 现有历史、日志、视图与解析预算不隐式放宽；需要调整时须证明它阻碍核心 Agent 工作流。
- 不默认启动付费 Agent、更改用户真实仓库/信任/系统权限、部署云服务或对外发布。真实验收优先使用隔离项目和无敏感数据的任务。
- 修改前检查当前工作区已有变更，避免覆盖正在进行的工作；每个实际修复切片开始前按图谱冻结影响范围。

## 8. 每个修复切片的闭环与交付规则

1. 图谱定位当前实现；明确一个用户可见结果、正常/边界/异常验收及原生平台。
2. 先补行为测试并观察实际语义失败；测试夹具/编译失败单独分类。
3. 最小实现；不通过牺牲输入正确性、权限或持久化换取响应指标。
4. 定向与受影响全量验证，再做当前构建的真实桌面操作。工具不能操作UI时明确未验收；给实际人工步骤，不以RPC/静态测试替代。
5. 若继续沿用用户此前授权的多模型模式：一个模型实施、另一个独立复审；共享仓库一个写入者。复审不等于用户体验验收。
6. 用户可见结果通过后才计为完成。原始日志写入外部归档，Git只保留必要源码/测试/配置、精简摘要和稳定复现夹具。
7. 阶段结束交付功能演示/操作说明、缺口列表与同版本回归数据；提交代码需沿用当轮明确授权，发布仍另行授权。

常规命令：`rtk proxy pnpm --dir apps/desktop test`、`rtk proxy pnpm --dir apps/desktop test:coverage`、`rtk proxy pnpm --dir apps/desktop build`、Rust目录的`rtk proxy cargo test --locked --offline -- --test-threads=1`、`rtk proxy cargo fmt --check`、`rtk proxy cargo clippy --locked --offline -- -D warnings`、`rtk proxy git diff --check`。原生验收步骤须在实际运行前确认，不发明尚不存在的测试命令。

## 9. 完成判定

本轮完成必须同时满足：

- 上述六条核心 Agent 工作流在目标桌面平台的当前构建中通过；不以旧构建、模拟回调、源码测试或打包成功替代。
- 影响 P0 的已知缺陷已修复并有回归验证；暂不支持的能力和协议差异写入用户可见说明。
- 用户能够按操作说明启动、并行管理、切换、恢复和安全停止 Agent。
- cmux 的全产品功能清单、移动端、Cloud、企业策略、完整远程工作区和任意插件能力均不作为本轮完成条件。
