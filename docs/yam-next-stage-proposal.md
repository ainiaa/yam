# YAM 多 Agent 工作台优化方案（待评审草案）

作者：Jeff.Liu。研究日期：2026-10-01。代码基线：0617b23（业务代码9affe4a）。修订日期：2026-10-01。

用户目标：功能比cmux更强、体验更好。第一阶段已确认优先“多Agent状态与通知准确、切换高效”。本文件是待验证的优化方案，本轮未实施功能、新增依赖、运行基准或修改CLI全局配置。

## 1. 交付目标与边界

目标用户为同时运行多个本地Codex/Claude会话的开发者。先打通“启动 → 准确识别每轮状态 → 收到有用提醒 → 快速回到正确会话 → 继续输入”的完整工作流。

第一阶段以Codex、Claude Code为集成目标，完成能力探测和真实验证后才列入正式支持矩阵。通用CLI保留终端及退出通知。OpenCode作为后续扩展验证对象。继续覆盖macOS/Windows/Linux，平台未实测时显示证据缺口。

YAM负责会话运行、状态呈现、通知、导航和对话恢复。Git worktree由用户、Git工具、IDE或Agent自行管理；YAM只使用用户选定的现有目录，不创建、删除或归档worktree，也不承担提交、合并和PR管理。权限/提问提醒用于引导用户回到CLI处理，本阶段不代替Agent作审批决定。

“更强、更好”需要同场景对照验证：轮次通知、需要介入提醒、未读信息保持、键盘到达、切换时上下文保持、故障后可恢复。第一阶段补齐交互事件能力，并争取在通知可解释性、跨平台一致性和注意力导航上形成优势。尚不声称全面超过cmux，也不预设Web终端性能会优于Ghostty。

## 4. 三条路线及选择

| 路线 | 收益 | 成本/限制 | 判断 |
|---|---|---|---|
| A：现有PTY + 官方Hook/notify + Rust状态与通知 | 保留完整交互终端，最少迁移，直达当前缺口 | 要维护CLI版本兼容；Hook并非所有最终结果的完整证明 | 推荐第一阶段 |
| B：Codex app-server/OpenCode server等结构化客户端 | 更丰富的消息、审批和可编程控制 | 各Agent协议不同，需重做部分交互体验；当前仅对OpenCode server做了文档核实 | 第二阶段按真实需求独立试验 |
| C：只识别屏幕文本/提示符与空闲 | 易接入任意CLI | 文本、主题、本地化、输出中的示例会造成误报；无法可靠定义轮次 | 仅保留为低可信提示，不发完成通知 |

保持Tauri 2、Rust、React、xterm与portable-pty。现阶段不引入中间件、SQLite、后台守护服务或全套插件框架。若基准证明历史扫描或原子保存占据主要延迟，先优化实际写入/读取路径；只有现有存储无法满足已确认的数据量、查询或一致性要求时，再单独评估迁移；新增依赖按用户约定单独确认。

## 5. 第一阶段设计

### 5.1 真实交互事件与状态

保留现有会话生命周期状态starting/running/succeeded/failed/stopped及恢复时的needs_attention；Agent轮次状态另存为idle、working、needs_permission、needs_input、response_finished、interrupted、error、unknown；后台任务另用none/pending/unknown字段，避免把“回复结束”和“后台仍运行”做成互斥状态。未收到可信事件时保持unknown，不能将其默认视为idle。用户界面分别显示“回复已结束”和“会话已结束”，不以Stop承诺需求全部交付或测试已通过。

先对每个正式支持的CLI版本探测Hook/notify能力，记录可用事件和可靠字段；不以最新文档假设本机支持。优先进程启动参数/会话配置注入，不覆盖用户原有Hook、不自动修改全局配置、不关闭用户安全检查。不支持安全注入时，明确降级为普通终端；全局安装只作为后续显式选项。

接入SessionStart、PromptSubmit、Stop/turn-complete以及确实支持的权限/中断/失败事件。缺少某种事件时显示该能力不支持；不能靠PTY字节输入猜测审批结果，不能把无输出当完成。

每个事件绑定YAM session、本次launch generation、source、kind及可获取的Agent session/turn ID。来源缺少Agent session ID时可以归属到已绑定的YAM会话，但不能据此提供原生resume。可靠来源提供turn/event ID时直接使用；没有时只有已验证的PromptSubmit边界和事件关联契约才可产生本地轮次。迟到且无法可靠关联的事件不得写入下一轮完成状态，记录“事件无法关联”。

Stop仅作为该适配器定义的回复结束信号，不证明测试通过、需求交付或后续不会继续运行。存在其他可阻止停止的Hook时，必须先验证是否能得到最终结果；不能得到时只显示“收到回复结束信号，最终状态未确认”，不发送确定完成横幅。短暂静默不能解决这个语义缺口。已确认回复结束且仍有后台任务时显示两项事实；不清楚后台状态时显示unknown。中断与错误独立记录，不转成成功。

通信实现尚未冻结。先核对现有Tauri/单实例能力能否支持不激活UI的受限事件入口；不适用时再比较带认证的loopback标准接口与简单本地连接，按跨平台可用性、依赖成本和失败行为选最小方案，不提前维护自定义协议。复用当前Rust二进制作为非UI Hook helper是待验证选项，不是已确定结构。

无论选择哪条路径，都必须限制为本机通信，绑定本次launch及目标会话，验证身份、消息大小与契约版本。不能从上报的任意sessionId自行建立路由；凭据不进入日志/命令参数/持久历史。身份凭据需要安全随机源，新增依赖另行确认。边界用于避免外部终端或旧进程误路由，不宣称防御已控制当前用户或Agent进程的攻击者。

若选择复用二进制helper，则在桌面应用的单实例/UI初始化之前分流，不激活窗口，不插入终端输出。遵守各CLI stdout响应契约，通知失败不阻断Agent；对客户端/连接设置短超时，失败显示集成降级。低频生命周期事件才落盘，不为每个tool输出启动额外进程。只有验证过启动开销、平台行为和CLI响应契约后才确定helper方案与注入参数。事件持久化成功后才在内部通信中确认接收；接收失败不能冒充提交成功。对CLI仍返回符合其契约的非阻塞响应，不能为通知错误阻止Agent正常完成；集成降级通过YAM诊断状态呈现。若Hook未执行或上报失败，不能承诺捕获所有事件，也不能仅凭没有事件判断CLI仍在工作。

### 5.2 通知收件箱和可靠回执

Rust核心统一处理可信事件、持久状态及原生通知。React订阅并呈现，UI重载不负责重新判断是否发送。沿用现有平台通知实现。

事件身份与状态revision分别设计。稳定事件身份用于识别同一次来源事件的重复上报，不能每次接收先生成新revision再作为去重键。缺少来源event ID时，按适配器契约定义轮次内的通知身份；重复权限请求等无法区分时要明确合并范围，不能宣称逐事件精确。独立revision用于状态顺序及旧ACK拒绝。

替换当前仅session:status的去重，至少区分session、launch generation、turn generation和通知类型。历史状态、收件箱条目及待发送回执写入同一原子保存边界；应用内事件提交后才尝试系统发送，发送成功才记录系统发送回执。ACK校验具体通知身份/revision，不只比状态文字，多个连续response_finished不能互相确认。

区分“系统API接受发送”和“用户已读”，系统API成功不等于用户看见。首版保存pending/accepted/failed/suppressed发送结果和read/unread阅读状态；权限/提问是否已解决由可信Agent事件决定，不额外发明手动“已处理”状态机。前台看着目标会话可以抑制横幅，但仍记录状态事件；切到另一个会话不抑制后台会话提醒。系统通知失败时保留应用内未读及可操作错误，沿用暂停永久错误和退避暂时错误的模式。

仅合并契约明确属于同一轮、同一次需要介入的通知；独立权限请求、错误或不同轮次不能被去重掉。子Agent身份与父子关联可核实时，默认聚合到父会话；无法核实时不凭标题猜测归属，也不新增子Agent编排。

系统通知保留稳定会话标识，通知中心可替换为该会话最新提醒；应用内收件箱保留各轮记录。首版点击定位会话并展示相关未读，不承诺现有仅session ID的系统路由能精确跳到历史某轮。若后续需要精确事件跳转，须单独扩展并验证激活协议及旧通知兼容。会话已退出时查看历史，继续运行是独立动作。

应用内记录可做到提交/去重不重复；操作系统发送与磁盘确认之间不能保证恰好一次横幅。保留稳定系统标识和现有崩溃回执测试。历史存储设置可验证的条目/字节预算：已读条目可以清理；过多未读可合并为会话摘要，并保留未读数量、事件范围与最新介入状态；需要保留完整细节时先导出再清理，只有摘要时明确告知细节已压缩，不承诺可展开恢复原记录。尚未成功发送的必要回执不能随普通历史淘汰。必要待发送回执达到预算且无法安全合并时拒绝确认新事件并提示容量问题，不无限增长，也不冒称可靠接收；具体预算依据B0/B1负载测量确定。

### 5.3 状态可见、切换省操作

侧栏每个会话显示Agent、项目目录、可信轮次状态、未读数与最近事件；既有进程终态作为单独信息。新增“需要我处理”集合，优先权限/提问、错误，其次回复结束。

键盘支持下一条未读、上一个会话、快速搜索切换、暂停/恢复提醒；快捷键可配置并考虑平台差异。鼠标点击和快捷键共用同一选择路径。用户主动选择会话后把焦点交给目标终端；后台事件和自动刷新不抢焦点、不自动切换会话。搜索框输入期间通知也不能把焦点移走。

新建会话用“持续对话”和“执行一个任务”的用户语言，并说明当前Agent完成提醒是否可用。保持用户保存的模式选择，本轮不改变默认模式；接入未就绪时明确显示仅支持退出/空闲提醒。

### 5.4 终端上下文与恢复

先测量现有日志读取、重放、绘制的耗时，定位切换瓶颈，并补滚动位置和焦点行为。保留少量独立xterm实例是候选优化，数量按实测内存预算确定，不预设必须使用三个或必须重构为多实例。后台实例若保留，就持续按顺序消费输出并保持正确PTY尺寸，避免隐藏DOM导致尺寸归零。

冷会话从有限日志重放只能保证已有日志片段可查看，不能保证完整重建alternate screen、光标和解析状态。需要完整TUI恢复的活跃会话不能在没有经验证的状态快照前按普通LRU释放。预算不足时保留可交互会话并限制打开数量或明确提示降级；不能声称截断日志可无损恢复。

不无限创建所有历史终端。记录终端缓存开销，仅在可恢复性验证通过的范围内释放实例。对alternate screen、颜色、光标、中文/emoji、快速输出/切换、窗口缩放和快捷键进行验收。

之后存储可信Agent session ID，仅对已验证恢复能力的版本提供用户主动原生resume继续同一对话；重新运行原命令另行标注。退出策略仍清理本应用进程，不把历史恢复宣传为原进程持续存活。仅使用已验证适配器构建resume参数，不恢复任意存储shell命令，不持久保存敏感环境变量。应用启动或通知点击不自动重新执行任务；缺失会话ID、目录、CLI/provider配置时给出明确原因，不自动退回新对话而冒充resume。

## 6. 分批执行与退出条件

| 批次 | 可交付行为 | 前置条件及主要检查 |
|---|---|---|
| B0：能力与技术验证 | 明确当前CLI版本是否能提供可靠轮次事件，给出支持矩阵和选定接入路径 | 真实双轮、其他Hook续跑、用户配置保持、非YAM会话隔离；失败时记录降级能力，不先承诺B1全支持 |
| B1：交互轮次通知 | 已验证版本连续两轮，进程不退出，每轮都有正确归属的后台提醒 | B0通过；先对一个Agent完成端到端切片，再适配另一个；稳定事件身份、原子持久回执和原生通知回归 |
| B2：介入收件箱 | 权限/提问/错误与回复结束分开；键盘一次到正确会话 | B1通过；按实际事件能力展示介入类别；合并/已读规则、前台抑制、父子身份与错误恢复测试 |
| B3：切换与终端保持 | 多会话切换保留上下文，界面响应可测量 | 测量现有瓶颈后选择方案；有界资源、可恢复性限制、TUI/Unicode/输出竞争、滚动与焦点验收 |
| B4：原生resume | 应用重启后可继续原Agent对话 | 可信session ID、版本契约；失效ID、缺失目录、移动CLI、升级/回退验证 |
| B5：跨平台可分发验证 | 三平台真实安装包上的全链路达到声明能力 | 各批次同步维护CI；三平台真实桌面点击/唤醒与正式签名证据齐全才能声明完整发布验收 |

B0为后续承诺提供实证，其余每批次交付一种用户可见闭环，按“规格/失败测试 → 最小实现 → 回归/静态检查 → 独立复核 → 文档证据 → 可回滚提交”推进。功能依赖顺序为B0→B1→B2，B3可独立于B2开展，B4复用已可信绑定的会话身份。平台验证从B0起逐批执行，B5集中核对发布证据；缺少某个平台桌面不阻止已验证平台的开发，但该平台保持未验收。依赖项的关键检查未通过，不实现依赖它的功能；不把研究草案直接当实现已获批。

实施文件预计触及agent_command/Session/HistoryStore、现有notifications及App选择流程；只围绕这些新增职责抽取小模块，避免改造整个仓库。JSON新增字段要有向后兼容默认值，迁移先使用副本；保留原记录/日志与备份，回退验证不能只依赖旧serde忽略未知字段。

当前不冻结周数排期：团队投入、CLI兼容性、通信验证和真实桌面资源尚未确定。B0结束后，用真实双轮接入工作量和终端性能基线估算各批次，并将证书/平台环境等待与开发时间分开。先完成一个Agent的纵向切片，再估算第二个，不在前置能力未知时承诺全部集成时长。

## 7. 可证伪的验收标准

下列均为拟定目标，尚未测量，不代表已超过cmux。

- B1按风险建立可重复执行的事件/持久层夹具，不以测试条数作为质量目标。至少覆盖：正常两轮、同会话反复完成、重复/乱序/跨launch迟到、两个会话并发、缺失ID、断连、非法凭据/大小、磁盘故障、Hook要求续跑、子Agent及后台任务；要求受控夹具中零串会话、零错误轮次ACK，已确认接收并持久化的必要事件在恢复后可用。同一事件重复回放只产生一条应用内记录。
- 使用barrier或可控mock在“事件持久化/发送/ACK”竞争点复现并发，断电/崩溃注入测试不得只用顺序重试替代。
- 每个列入支持矩阵的Agent/CLI版本执行真实交互冒烟，逐项覆盖双轮、权限等待、恢复输入、正常回应、中断和异常；未提供某种事件的版本按降级能力验证。测量Hook发出、核心接收、原子提交、UI呈现与系统API接受五个阶段的延迟；应用内提醒目标为Hook发出后1秒内，系统横幅何时显示受OS控制，不能纳入同一承诺。真实冒烟样本不能冒充统计显著的可靠性百分比。
- Hook注入前后用户配置逐字比较，外部终端运行同CLI无YAM事件；现有用户Hook仍执行，审批/沙箱行为保持用户设置。
- 先在同一Mac、同一CLI版本、窗口/PTY尺寸和固定输出夹具下对比cmux/YAM；记录硬件、应用版本、会话数和日志大小。分别测单会话、常用多会话及压力负载，重复采样切换耗时；定义终点为目标会话首次可见且可接受输入。核心体验要求：一条快捷键到下一条未读、快速切换不串输入、不改变目标会话原有阅读位置。150ms热切换/500ms冷切换仅保留为待基线确认的候选预算，不作为未经测量的发布硬门槛。
- 30分钟固定输出压力测量YAM主应用资源（与Agent进程资源分开）；预热后内存不能无界增长，停止会话后缓存按策略释放。不得只凭Tauri技术选择声称比cmux轻。
- macOS/Windows/Linux分别记录真实桌面结果，包括前台目标抑制、后台会话提醒、通知关闭后的收件箱、点击定位、退出后保存通知唤醒，以及正式包升级/路径变化。CI编译不等价点击验收。

## 8. 后续可评估范围

后续能力仍围绕会话管理：按需求验证OpenCode等CLI事件适配、会话日志搜索/导出、原生续聊兼容性以及提醒偏好。Git worktree、代码审查、测试编排、提交和PR交付不进入本方案。用户可把外部工具管理的任意现有目录交给YAM运行。

有明确需求时，用一个独立切片验证OpenCode原生事件及跨Agent状态契约。只有消息/权限卡片确实需要更深控制时再评估Codex app-server；不在PTY路径里模拟审批决策。远程Agent、团队编排、浏览器和账号云同步不列为承诺路线；只有用户提出明确需求后才单独设计。

## 9. 反转条件与已知限制

如果目标CLI版本无法安全限定Hook到YAM进程，或Stop无法可靠关联轮次，就不能发布“准确完成通知”的声明；降级为状态未知/退出通知，评估该Agent原生结构化协议替代路径。当前退出策略会终止YAM管理的进程；“退出后继续后台运行”属于另外的需求，未纳入本阶段，也不通过自动resume模拟。

现有跨平台桌面、Developer ID证书、遗留通知样本、Rust覆盖工具及外部CLI复审缺口仍保留在notification-acceptance.md和reliability-followup-plan.md；本方案不把这些标记为完成。

本轮仅修订方案草案，待用户评审后从B0验证开始，不直接执行业务实现。
