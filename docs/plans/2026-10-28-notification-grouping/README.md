# macOS 通知归组与降噪

作者：Jeff.Liu

## 行为

- 使用项目工作目录的 SHA-256 作为 macOS 通知分组标识，不再把会话跳转链接放进分组字段。不同目录的同名项目互不混组。
- 项目内按完成、失败、授权、其他待关注事件分开合并。相同项目、相同类别、相同 10 秒时间桶使用同一请求标识，以 2 秒非重复系统触发器合并尚未弹出的连续提醒；最新请求保留自己的标题、内容和跳转目标。
- 跳转链接单独保存在 `targetContentIdentifier`，兼容历史通知中线程字段或请求标识保存的会话链接。普通完成消息不会覆盖失败或授权提醒。
- 用户主动停止的会话不生成待发通知，共享原生发送入口也会抑制这类提醒。旧待发记录不会重新排队；后台恢复时持久清除其待发标记，避免继续阻碍归档。
- 保留收件箱事件、暂停设置、权限错误、发送失败重试和异常停止提醒。不新增设置或依赖。

这是固定时间桶内对系统待发请求的替换，不是无限延迟的防抖，也不承诺跨时间桶只出现一张卡。系统如何折叠已送达通知仍取决于 macOS 通知设置；已有通知不会自动重新归组。

## 验证

先运行分组身份和主动停止静默测试得到失败结果，再修改实现；旧记录待发过滤和持久恢复分别记录红绿证据。

- 前端：2041 项，2038 通过、3 项浏览器显式启动测试跳过。
- Rust 全量：1060 通过、25 项显式原生验收测试忽略。一次高并发全量中有两个未修改模块测试失败，单独复验均通过；随后限制测试线程的完整回归通过。原始日志保留。
- 最后的旧记录恢复调整追加验证：78 项历史测试、主动停止与重新打开记录的回归均通过。
- macOS SDK 请求测试验证项目隔离、时间桶边界、重要类别隔离、2 秒非重复触发、最新会话跳转、旧链接兼容和权限错误。
- 独立只读 CLI 复核：需求复核、原生发送顺序复核和最终旧记录兼容性复核通过。顺序复核核实了已有全局发送门和同步 worker join，不新增排序队列。
- 构建及安装同一个 `YAM.app`，标识保持 `com.yam.desktop`，版本保持 `0.1.10`；签名、主程序与后台 helper 一致性验证通过。
- 使用已有原子空闲更新机制重启无活动任务的后台。安装后创建一个专属临时 shell 并主动停止，确认待发标记为 false、待发接口不返回它、直接通知请求被共享入口静默处理。
- 验收暂时暂停通知并以修订号保护恢复原设置；测试会话已归档，活动会话 0，总会话数回到 155。没有批量发送系统测试弹窗。

证据位于 `.artifacts/notification-grouping-20261028/`，包括红绿日志、`rust-tests-final.log`、`history-tests-final.log`、`frontend-tests.log`、`review-*-result.json`、`bundle-final.log`、`verify-installed-final.log`、`owner-update-proof.json`、`native-quiet-proof.json` 和 `cleanup.json`。

未执行 Windows/Linux 通知分组或 macOS 通知中心批量弹窗视觉验收；使用真实 SDK 请求对象验证分组元数据及调度参数，以免再次打扰用户。此次独立复核使用本机 CLI 原配置，未测算费用。
