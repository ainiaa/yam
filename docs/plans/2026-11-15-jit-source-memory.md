## 顺序与证据

1. 冻结源码/包和旧五项门槛，校验计划，复用已有诊断清场和进程身份工具。先测试新增地址/源码映射解析的正常、边界、冲突与异常场景。
2. 优先在不改产品包的情况下生成隐藏source map，必须证明生成JS与现有前端资产逐字节相同。读取本机/上游JSC可用JIT标记或JITDump机制；单次最多180秒，临时环境仅作用于规范App，记录是否被本机支持或沙箱拒绝，不改权限。新窗口必须同时生成新地址映射和对应原生栈，绝不跨进程映射旧地址。最多一个JIT标记模式和一个确有方法变化的后备模式。
3. 使用Inspector在owned合成任务上取得应用调用来源和实际持有路径。先用AX setValue和Command-Return执行完整表达式，避免上轮自动补全问题；每次观察只导出必要的类、函数位置、引用边和标量，不导出用户对象内容。窗口和采样阶段分别记录，不将Inspector时的数值纳入五项产品门槛。若地址标记受平台限制，保留失败，改用引擎分配/保留图和同源码位置的实测调用计数作交叉证据，不声称完成了地址符号化。
4. 对已证实根因检查调用者与生命周期，先补可执行失败测试，再做最小修复。分别处理存活对象、暂存数据、渲染分配和引擎堆块/碎片；没有应用可达链的部分不得猜修或强制GC。根因超出下列冻结范围时先更新计划范围及验证命令。
5. 跑定向回归、必要覆盖率、正式规范包构建和独立源码复核。业务源码未改部分不重复Rust全量；修改后沿用既有覆盖率路线。最终同包使用原命令、原几何和负载检验五项门槛，保留全部失败，不挑最小值。最多两个有实质不同修复的产品候选；同源码/包不反复重跑取较好结果。
6. 候选变化后补齐16测试视图前置及完整8小时，保留全部采样尝试，不能拼接运行。清理owned任务，恢复原始通知策略、普通运行环境和唯一GUI，核对包/已安装版本/未读数。最终审计如实区分通过、失败与未覆盖。
